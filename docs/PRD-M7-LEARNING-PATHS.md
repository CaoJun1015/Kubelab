# KubeLab M7 产品需求文档——专题学习路径

> 文档版本：v1.0
> 文档状态：待评审
> 建议开发版本：`0.4.0a0`
> 前置条件：M6.1完成并发布KubeLab `0.3.0`
> 适用平台：WSL2 Ubuntu + 本机minikube

---

## 1. 产品定义

M7将KubeLab从“实验目录”升级为“有先后关系、有掌握标准、有复习建议的专题学习系统”。

系统不再只把21个实验族平铺给用户，而是围绕真实排障能力组织学习路径，引导用户依次完成知识准备、原始基线、固定变体、综合故障和专题复盘。

M7继续遵守KubeLab的核心边界：Web负责发布任务、展示证据和记录成果；用户在受限WSL Workspace中调查和修复；Application Service统一管理实验生命周期。

## 2. 背景与问题

M6已经具备21个实验族、12个固定变体和33个可执行场景，但仍存在以下学习问题：

1. 用户知道“有哪些实验”，却不清楚应该先练什么、后练什么。
2. 单次通过可能来自记忆答案，不能证明知识已经迁移到相似故障。
3. 基线、变体和双根因综合实验之间缺少显式的能力递进关系。
4. 当前进度按实验展示，不能回答“Service排障专题是否真正掌握”。
5. 用户看到症状时，不容易找到对应的练习入口。
6. 提示次数、验证次数和完成耗时已有记录，但还没有形成可解释的复习建议。

## 3. 产品目标

### 3.1 核心目标

1. 用户进入KubeLab后能够获得唯一、明确且可解释的下一步练习建议。
2. 通过“基线 → 变体 → 综合故障”验证知识迁移，而不是只验证答案记忆。
3. 将现有21个实验组织为4条专题路径，不复制Session或完成状态。
4. 在实验前提供必要概念和证据清单，在通过后揭示根因、最小修复和预防措施。
5. 支持从常见Kubernetes症状反向进入相关知识和实验。
6. 根据既有学习事实生成确定性复习建议，不引入隐式分数或排名。

### 3.2 成功标准

- 新用户能够在3次点击内进入推荐的首个实验。
- 每个综合实验都有明确、可验证的前置解锁条件。
- 路径进度与现有Session事实保持一致，不产生双重状态。
- 未通过的盲练场景不会通过路径页、知识卡、时间线或API泄漏答案。
- 用户能够解释一个专题的典型症状、调查证据、根因类型和预防方法。

## 4. 非目标

M7不实现：

- 随机练习入口；
- 限时面试、评分、排名或能力等级；
- AI自动诊断、自动修复或生成答案；
- 浏览器终端、在线YAML编辑器或任意Shell输入；
- 用户选择尚未揭示的具体变体；
- 新增实验、验证器或远程集群支持；
- 独立于Session的第二套完成状态；
- 社区账号、云同步或多人教学管理。

## 5. 目标用户与核心任务

### 5.1 初次系统学习者

希望按合理顺序掌握Kubernetes排障，不想自己判断21个实验的学习次序。

核心任务：查看推荐路径，理解本节目标，完成基线练习，并知道下一步为什么被解锁。

### 5.2 已完成部分实验的复习者

已经完成若干实验，希望补齐薄弱知识或练习变体。

核心任务：从症状索引或专题报告进入建议节点，重复练习但不直接看到变体答案。

### 5.3 面试准备者

希望把零散操作整理成可表达的调查方法。

核心任务：完成综合场景，查看专题复盘，并用“现象—证据—根因—修复—预防”表达案例。

## 6. 产品原则

1. **路径组织知识，Session记录事实。** 路径不保存独立完成状态，所有结果从Session、事件、提示和验证记录派生。
2. **首次基线，完成后变体。** 继续沿用M6确定性场景选择规则，不增加随机选择。
3. **先观察，后揭示。** 通过前只展示现象、目标和调查框架；通过后才展示场景根因与标准修复。
4. **解释每个门槛。** 锁定节点必须明确显示尚缺少的前置练习，不使用不可见分数。
5. **推荐可以忽略，安全边界不能绕过。** 用户仍可从实验目录启动已允许的普通实验，但不能手动指定隐藏变体。
6. **内容与运行时分离。** 路径定义只组织已有实验，不直接操作Kubernetes。

## 7. 专题路径

一个实验族可以出现在多条路径中，但同一次成功只记录一份Session事实，并同时影响相关路径的派生进度。

### 7.1 工作负载生命周期

覆盖Pod创建、镜像拉取、进程退出、健康检查、Job和DaemonSet等控制器行为。

包含：`LAB-001`、`LAB-002`、`LAB-004`、`LAB-005`、`LAB-006`、`LAB-010`、`LAB-015`、`LAB-017`。

学习成果：能够从Pod phase、container state、Events、Logs和控制器状态判断故障发生在调度、拉取、启动、运行还是健康检查阶段。

### 7.2 配置与应用依赖

覆盖环境变量、ConfigMap引用、容器参数以及配置与Service的串联影响。

包含：`LAB-003`、`LAB-008`、`LAB-014`、`LAB-019`。

学习成果：能够区分配置对象不存在、对象存在但key错误、应用配置错误和配置修复后仍存在的下游故障。

### 7.3 服务发现与流量链路

覆盖Service selector、port/targetPort、Endpoint、Headless Service、DNS和HTTP可用性。

包含：`LAB-007`、`LAB-009`、`LAB-011`、`LAB-013`、`LAB-016`、`LAB-021`。

学习成果：能够沿“调用契约 → Service → Endpoint → Pod端口 → DNS/HTTP”逐层定位流量故障。

### 7.4 存储与调度

覆盖节点约束、PVC创建和绑定、StorageClass、挂载权限及存储与readiness的组合故障。

包含：`LAB-012`、`LAB-017`、`LAB-018`、`LAB-020`。

学习成果：能够区分调度条件、PVC绑定、卷挂载、容器读写权限和应用健康检查问题。

## 8. 学习节点模型

每条路径由以下五类节点构成：

1. **概念导入**：说明是什么、为什么重要、主要对象和常用证据。
2. **基线实验**：首次固定使用原始故障，建立稳定调查方法。
3. **变体复练**：由服务端按M6规则选择固定变体，检验知识迁移。
4. **综合实验**：同时包含两个根因，要求用户分阶段验证假设。
5. **专题复盘**：汇总已完成事实、典型证据、已揭示场景和复习建议。

概念导入和专题复盘是内容节点，不创建Session。实验节点继续使用现有实验启动、恢复、验证、reset和cleanup流程。

## 9. 解锁规则

### 9.1 通用规则

- 概念导入默认可访问。
- 实验族的首次练习固定为`baseline`。
- 同一实验族的基线首次通过后，允许进入变体复练。
- 综合实验只有在对应基础能力完成后才解锁。
- 清理不是学习完成的前置条件；`success_contract_passed`仍是能力完成事实。
- 活动Session优先于新推荐，用户必须先恢复或清理当前Session。

### 9.2 综合实验前置条件

| 综合实验 | 硬性前置条件 |
|---|---|
| `LAB-019 configuration-service-chain` | `LAB-013`基线通过；`LAB-014`基线通过且至少一个变体通过 |
| `LAB-020 storage-readiness-chain` | `LAB-009`基线通过；`LAB-012`基线通过；`LAB-018`基线通过且至少一个变体通过 |
| `LAB-021 stateful-service-chain` | `LAB-013`基线通过；`LAB-016`基线通过且至少一个变体通过 |

### 9.3 节点状态

页面可显示以下派生状态：

- `available`：可开始；
- `active`：存在该节点对应的活动Session；
- `completed`：满足完成事实；
- `locked`：前置条件未满足；
- `review_recommended`：已完成，但满足复习规则。

这些状态每次读取时计算，不持久化为业务状态。

## 10. 核心用户流程

### 10.1 首次进入

```text
Dashboard → 推荐“工作负载生命周期” → 阅读概念导入
→ 启动首个基线实验 → 在Workspace排查 → Web验证
→ 查看通过后知识卡 → 获取下一个明确节点
```

### 10.2 基线完成后的复练

```text
路径页显示“变体复练” → 服务端确定性选择场景
→ 盲练阶段只显示现象与通用目标 → 使用分层提示或自行调查
→ 验证通过 → 揭示场景、根因、最小修复与预防措施
```

### 10.3 综合故障解锁

```text
完成硬性前置节点 → 综合实验从locked变为available
→ 用户依次定位两个根因 → 第一个修复后验证仍未通过
→ 根据新证据继续调查 → 全部成功条件通过 → 完成专题复盘
```

### 10.4 从症状进入

```text
症状索引 → 选择“有Endpoint但HTTP失败”
→ 查看相关证据顺序和已解锁实验 → 进入推荐节点
```

## 11. 功能需求

### FR-M7-001 路径首页

- Dashboard将“继续当前Session”和“推荐下一步”放在实验目录之前。
- 展示4条路径的名称、目标、派生进度、当前节点和推荐原因。
- 无活动Session时只给出一个主要推荐动作。
- 实验目录继续保留为资源库入口。

### FR-M7-002 路径详情与能力地图

- 展示节点顺序、类型、状态和节点之间的前置关系。
- 锁定节点显示具体缺失条件，例如“完成LAB-014基线并通过任一变体”。
- 同一实验出现在多条路径时，不重复计算Session或练习次数。
- 支持跳转至既有实验详情、活动Session和复盘页面。

### FR-M7-003 实验前知识卡

每个实验节点在开始前展示：

- 这个知识点是什么；
- 为什么会影响业务；
- 本次成功目标；
- 建议关注的Kubernetes对象；
- 不包含答案的证据检查清单。

知识卡不得展示未揭示变体名称、根因、标准修复、完整Manifest或内部验证值。

### FR-M7-004 实验后知识卡

场景通过后展示：

- 现象与关键证据；
- 根因；
- 最小修复；
- 常见误区；
- 预防措施；
- 与相邻知识点的关系。

基线内容使用现有实验公开材料；变体内容继续遵守M6揭示条件。

### FR-M7-005 推荐下一步

推荐器使用固定、可解释的优先级：

1. 恢复活动Session；
2. 完成当前路径中已开始但未通过的节点；
3. 完成当前路径的下一个基线；
4. 完成解锁综合实验所需的变体；
5. 完成已解锁的综合实验；
6. 复习满足复习规则的已完成节点；
7. 开始尚未学习的路径。

响应必须包含可供UI显示的推荐原因，不允许使用不可解释的模型分数。

### FR-M7-006 复习建议

以下任一条件成立时可标记`review_recommended`：

- 基线已通过，但该实验族尚无变体通过；
- 最近一次同族练习未通过或中断；
- 最近一次通过使用了全部三层提示；
- 最近一次通过前手动验证次数达到4次或以上；
- 综合实验已解锁但尚未通过。

建议只使用现有记录派生，不保存“薄弱分数”。首版不按经过天数强制复习，避免引入不稳定的时间算法。

### FR-M7-007 症状索引

首版固定支持：

- Pod Pending；
- Running但NotReady；
- CrashLoopBackOff；
- ImagePullBackOff；
- Service无Endpoint；
- Service有Endpoint但HTTP失败；
- PVC Pending；
- Job Failed；
- StatefulSet稳定DNS失败。

每个症状条目展示定义、优先证据、常见原因分类和相关实验。症状页不根据真实集群状态自动诊断，也不返回修复命令。

### FR-M7-008 专题学习成果

专题报告从既有事实派生并展示：

- 基线完成数；
- 变体完成数；
- 综合实验完成状态；
- 已揭示故障类型；
- 提示请求数与手动验证数；
- 首次完成时间与最近练习时间；
- 当前复习建议；
- 可导出的脱敏Markdown专题复盘。

专题报告不得形成新的评分、等级或排名。

### FR-M7-009 内容注册与校验

- 路径和知识卡采用仓库内声明式定义，并在启动时严格校验。
- 路径只能引用Registry中存在的实验族。
- 必须拒绝循环依赖、重复节点、未知实验、无效前置关系和孤立综合实验。
- 任一路径定义无效时，该路径不可展示；不得影响无关实验的CLI操作。
- 运行时继续由`LabManager`解析实验和Session，路径层不得直接调用Kubernetes Client。

## 12. 页面与API影响

### 12.1 页面

- Dashboard：增加“继续练习”“推荐下一步”和路径摘要。
- `/paths`：专题路径首页。
- `/paths/{path_id}`：路径详情、节点地图和解锁原因。
- `/symptoms`：症状索引。
- `/paths/{path_id}/outcome`：专题学习成果和Markdown导出。
- 现有实验详情：增加前置知识卡、所属路径和通过后知识卡。

### 12.2 建议API

- `GET /api/v1/learning-paths`
- `GET /api/v1/learning-paths/{path_id}`
- `GET /api/v1/learning-paths/recommendation`
- `GET /api/v1/symptoms`
- `GET /api/v1/learning-paths/{path_id}/outcome`
- `GET /api/v1/learning-paths/{path_id}/outcome/export`

M7新增接口以只读为主。实验启动继续使用现有start API，不接受`variant_id`或客户端提交的节点完成状态。

## 13. 数据与状态原则

- 不新增路径进度表。
- 不在Session中新增“路径阶段”业务字段。
- 路径状态从`lab_session`、`session_event`、`hint_usage`和`verification_run`派生。
- 路径定义和知识内容属于版本化静态内容，不写入用户数据库。
- 若未来需要保存用户选择的当前路径，只能保存导航偏好，不能作为完成事实。
- 旧数据库升级后应立即得到正确路径进度，无需回填第二套记录。

## 14. 安全与隐私要求

1. 继续固定监听`127.0.0.1:8765`。
2. Web不得执行修复命令、启动CLI子进程或直接访问ORM/Kubernetes Client。
3. 动态内容必须使用Jinja自动转义或DOM `textContent`。
4. 路径、推荐、症状和专题报告DTO不得包含Secret、凭证、完整Manifest、expected/actual、异常正文或堆栈。
5. 变体通过前，所有新增页面和API都必须保持盲练边界。
6. Markdown导出必须执行现有脱敏、HTML中和和长度限制。
7. 若新增写API，必须继续执行Origin和CSRF校验；首版应优先避免新增写状态。

## 15. 测试与验收

### 15.1 功能测试

- 4条路径的节点、顺序和交叉引用准确。
- 新数据库和已有M6数据库均能正确派生路径进度。
- 活动Session始终成为最高优先级推荐。
- 三个综合实验的解锁条件逐项生效。
- 重复完成同一实验不会伪造额外路径节点。
- 复习规则在边界次数上行为稳定。
- 症状索引映射到正确实验，未知症状返回稳定错误。
- 专题报告与现有实验进度、复盘统计一致。

### 15.2 安全测试

- 未通过变体在路径页、推荐原因、知识卡、专题报告和Markdown中均不泄漏。
- 恶意HTML只作为文本显示。
- Secret、Bearer token、kubeconfig、Manifest、内部验证值和异常堆栈不会进入公共DTO。
- 页面GET不运行Doctor、kubectl、minikube或任何系统命令。

### 15.3 工程验收

- 优先使用Fake Application Service和临时SQLite，不访问真实minikube。
- Windows与WSL分别通过pytest、覆盖率不低于90%、Ruff、format check、strict mypy、JavaScript语法检查和`git diff --check`。
- wheel/sdist包含全部路径和知识卡定义，并能在隔离安装环境中加载。
- M6的21个实验族、12个变体和33个场景回归通过。

## 16. 指标

### 16.1 核心指标

- 路径入口使用率；
- 基线通过后进入变体的转化率；
- 综合实验解锁率与完成率；
- 专题复盘完成率；
- 推荐节点被采纳的比例。

### 16.2 诊断指标

- 用户在路径页到启动实验的耗时；
- 使用三层提示后仍未通过的Session比例；
- 同一节点中断后恢复完成的比例；
- 症状索引到实验启动的转化率。

所有指标仅面向本地派生展示；M7不增加遥测上传。

## 17. 分阶段交付

### M7.0 路径与内容契约

- 确定声明式路径Schema、4条路径和知识卡字段。
- 完成循环依赖、实验引用和盲练内容边界测试。

### M7.1 路径入口与派生进度

- 实现路径Registry、路径首页、详情页和派生节点状态。
- Dashboard以活动Session和推荐下一步为主要入口。

### M7.2 解锁与确定性推荐

- 实现综合实验前置条件、锁定原因和固定推荐规则。
- 保证启动接口不接受变体选择或客户端完成状态。

### M7.3 两阶段知识与症状索引

- 增加实验前/后知识卡和9类症状入口。
- 完成盲练泄漏测试和内容校验。

### M7.4 专题成果与稳定验收

- 增加专题报告和脱敏Markdown导出。
- 完成Windows、WSL、构建产物和现有33场景回归。

## 18. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
