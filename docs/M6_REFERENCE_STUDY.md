# KubeLab M6 参考研究：K8S 教学实训平台

> 研究对象：<https://k8s.sunnysfamily.hk/>  
> 研究日期：2026-08-29  
> 用途：为 KubeLab M6 的主体方针提供产品与内容组织参考，不构成对该网站实现方式的照搬。

## 1. 访问范围与结论可信度

本次未能在浏览器中完整渲染并交互操作该网站。浏览器访问发生超时，未登录，也未进入实际实验环境。

已成功通过 HTTP 访问以下公开内容：

- 首页 HTML，响应为 `200 OK`；
- 公开前端静态资源和 Vue 路由；
- 公开课程目录 API；
- 公开课程详情、章节、实验预览和部分实验指南；
- 前端中公开的实验 Session、环境信息、学习进度和页面交互逻辑。

因此，本文对课程结构和公开内容的描述有直接数据依据；对实验页面布局及交互方式的描述来自前端代码分析，尚未经过登录后的实际操作验证。

## 2. 总体判断

该平台最值得 KubeLab 学习的不是浏览器终端、在线编辑器或远程集群，而是以下三点：

1. 用较宽的故障主题组织多个具体故障表现；
2. 用“现象—根因—调查入口”建立故障全景；
3. 将课程内容、运行环境和学习进度放在一个连续的学习体验中。

这与 M6 当前讨论方向一致：M5 已经解决首次引导式排障闭环，M6 应重点解决重复练习时的答案记忆问题，使用户能够把同一知识应用到不同故障表现中。

## 3. 值得学习的设计

### 3.1 以故障家族组织内容

该平台的 Kubernetes 内容使用了以下主题：

- Pod 调度故障；
- Pod 运行故障；
- Service 网络故障；
- 镜像拉取故障；
- 存储故障；
- DNS 故障；
- 安全权限故障。

这些名称描述的是问题域，而不是单一错误字段。其“Pod 起不来”课程还把 ImagePullBackOff、CrashLoopBackOff、OOMKilled 和 Pending 放在同一主题中，用于建立系统化排障思路。

这对 KubeLab 的直接启发是：实验 ID 可以保持稳定，但显示名称和学习目标应从具体错误提升为故障知识单元。

| 实验 ID | 当前基线故障 | M6 建议知识单元 |
|---|---|---|
| LAB-013 | Service `targetPort` 错误 | Service 流量转发异常 |
| LAB-014 | ConfigMap 缺少键 | 工作负载配置引用异常 |
| LAB-015 | Job 命令失败 | Job 执行失败 |
| LAB-016 | Headless Service selector 错误 | StatefulSet 稳定网络异常 |
| LAB-017 | DaemonSet `nodeSelector` 错误 | DaemonSet 调度异常 |
| LAB-018 | Deployment 引用不存在的 PVC | 工作负载存储声明异常 |

知识单元名称变宽后，baseline 和 variants 才能承载不同根因，而不是只替换端口、键名或资源名称。

### 3.2 建立“故障全景图”

公开实验内容会将现象、根因和调查入口并列展示。例如针对 Pod 启动异常，可以形成如下认知结构：

| 现象 | 常见根因 | 首要调查入口 |
|---|---|---|
| ImagePullBackOff | 镜像、标签或认证错误 | Pod Events |
| CrashLoopBackOff | 进程启动后退出 | logs、退出状态 |
| OOMKilled | 内存限制过低 | Last State、Reason |
| Pending | 调度条件无法满足 | Pod Events、调度约束 |

KubeLab 可以借鉴这种知识结构，但必须采用渐进式披露：

- 首次练习前只介绍知识边界；
- 基线完成后解锁该场景的现象、关键证据和根因；
- 每完成一个变体，再解锁对应场景；
- 未覆盖变体不提前公开根因；
- 全部完成后形成该知识单元的完整故障全景图。

这样，全景图既是学习材料，也是由真实练习逐步形成的学习成果。

### 3.3 让任务、环境和证据保持上下文连续

从公开前端逻辑可以看到，实验页面会集中展示：

- 实验指南；
- Session 状态和有效期；
- Namespace；
- Pod 和 Service 摘要；
- 环境入口；
- 当前实验标题；
- 学习辅助区域。

KubeLab 不需要复制其三栏界面，但应借鉴“关键上下文无需离开当前任务页面”的原则。M6 页面应持续显示：

- 当前知识单元；
- 本次是否为首次练习或复练；
- Namespace；
- 固定 Workspace 入口；
- 当前 Session 阶段；
- 公开资源摘要；
- 最近验证结果；
- 已解锁的提示；
- 变体覆盖情况。

### 3.4 明确活动环境和继续学习入口

该平台的学习进度页面同时展示课程完成比例和正在运行的实验，并提供重新进入与停止环境的入口。

KubeLab M5 已经实现了更严格的活动 Session 恢复。M6 应在此基础上保持以下体验：

- 有活动 Session 时优先恢复，不创建新场景；
- 显示当前 `lab_id`、`variant_id`、Namespace 和阶段；
- 浏览器或 KubeLab 重启不改变当前变体；
- reconcile 必须由用户显式触发；
- reset 继续使用相同变体和 Seed。

### 3.5 内容按调查路径分层

该平台的高级排障课程覆盖调度、运行、网络、存储、DNS 和权限等常见问题域。这种分类方式适合用于检查 KubeLab 内容覆盖是否均衡。

M6 的每个变体不应只要求“修复一个不同字段”，还应明确它相对于基线改变了哪一段调查路径：

- 首先观察哪个对象；
- Events、logs 或资源状态提供什么证据；
- 哪个假设会被排除；
- 最终修改哪个故障字段；
- 如何证明修复不仅让对象存在，而且恢复了业务行为。

只有调查路径发生有意义变化，才应计为独立变体。

### 3.6 用完整故障链设计综合实验

参考平台覆盖了大量真实运维问题域，但不少公开内容仍以分步骤跟做为主。KubeLab 可以进一步把这些知识组织成可验证的双根因综合场景：

```text
根因一
→ 初始故障现象
→ 修复根因一
→ 暴露第二阶段现象
→ 发现根因二
→ 最终业务验证通过
```

例如：

```text
ConfigMap 键缺失
→ Pod 无法创建容器
→ 修复 ConfigMap
→ Pod Running
→ Service targetPort 仍然错误
→ 修复 Service
→ HTTP 验证通过
```

这种“连续暴露型”场景能够训练用户在第一次修复后重新观察系统，而不是看到部分恢复就停止调查。

## 4. M6 可采用的主体方针

结合参考研究和当前讨论，M6 可以定义为：

> **KubeLab M6——可复现故障变体与综合排障场景**

优先级确定为：

1. 同一知识点的不同故障表现；
2. 双根因综合故障；
3. 重复练习时的渐进式盲练。

不把智能推荐作为 M6 主体，不实现随机实验入口，不实现限时面试模式。

### 4.1 首次练习与变体轮换

确定采用以下规则：

```text
尚未成功完成知识单元
→ 始终使用原始基线

原始基线成功完成
→ 选择未完成变体
→ 全部覆盖后选择最久未练变体
```

补充约束：

- 启动、验证失败或中断不算基线完成；
- 未完成的变体在下一次练习时继续使用；
- 一个 Session 创建后，`variant_id` 固定；
- reset、恢复和 reconcile 不更换变体；
- 旧数据库中已完成的实验视为基线已完成；
- 新增变体不能降低用户已有完成进度。

### 4.2 进度语义

继续保留现有“完成”语义，并增加派生的变体覆盖展示：

```text
LAB-013：已完成
变体覆盖：2/3
最近复练：2026-08-29
```

不新增第二套完成状态，不使用评分、排名、考试通过或熟练度等级。

### 4.3 渐进式盲练

首次练习可以显示完整实验标题、目标和三级提示。基线完成后的复练默认隐藏：

- 具体变体名称；
- 明示根因的标题；
- 建议从哪个资源开始调查；
- 成功验证的内部结构。

复练仍允许用户主动解锁提示，不设置倒计时或提示惩罚。完成后再展示本次变体、根因、关键证据和与上次练习的差异。

## 5. 不应照搬的实现

### 5.1 浏览器终端和在线编辑器

参考平台公开前端包含 Web Terminal、Monaco YAML 编辑器、code-server、SQL 编辑器和 AI 对话区域。

KubeLab 必须继续遵守现有产品边界：

- 不实现浏览器终端；
- 不实现在线 YAML 编辑器；
- Web 不执行任意 Shell；
- Web 不启动 CLI 子进程；
- 用户只在受限 WSL Workspace 调查和修复。

### 5.2 页面加载自动启动环境

参考平台的公开前端逻辑会在进入实验页后调用 start。KubeLab 不应照搬：

- 页面 GET 不产生集群写入；
- start 必须由用户明确触发；
- start 前必须执行新鲜 readiness 检查；
- 环境不满足要求时在 Session 或集群写入前阻断。

### 5.3 提前展示完整答案

公开实验预览通常包含完整 Manifest、预期错误、调查命令和修复路径。这适合跟做式课程，但不适合 KubeLab 的复练目标。

KubeLab 应继续通过公开 DTO 和分层提示控制答案披露，不向 Web 返回完整 Manifest、expected/actual、Secret、凭证或验证内部值。

### 5.4 手动声明完成

KubeLab 不允许用户仅点击按钮声明完成。完成必须来自 Application Service 执行成功契约验证，并继续记录公开验证结果、证据摘要和完成时间。

### 5.5 扩大集群权限

参考内容包含 Node、`kube-system`、CoreDNS、集群级资源和较宽 RBAC 的调查示例。KubeLab M6 不应因此扩大权限范围，也不增加远程或生产集群控制。

## 6. 建议的实施节奏

### M6.1：LAB-013 纵向样板

- 建立 baseline/variant Schema；
- 为 Session 增加 `variant_id`，不引入随机种子；
- 实现基线优先和未完成变体优先；
- 为 LAB-013 增加两个有不同调查路径的变体；
- 打通 start、verify、reset、cleanup、恢复和升级迁移；
- 完成 Fake Gateway、Windows、WSL 和真实 minikube 验收。

### M6.2：扩展六个中级知识单元

- LAB-013～018 各提供 baseline 和两个变体；
- 增加变体覆盖统计；
- 增加知识单元故障全景图；
- 验证 12 个新增变体均有不同的关键调查证据。

### M6.3：渐进式盲练

- 首次练习维持完整引导；
- 复练只展示现象和公开证据；
- 完成后揭示变体和对比复盘；
- API 层而非仅前端负责隐藏答案。

### M6.4：综合排障场景

- 新增三个双根因综合实验；
- 每个综合实验包含明确的中间恢复状态；
- 最终成功条件必须验证业务行为；
- 不引入考试模式、倒计时或评分。
